# 终末地内容分类与跨来源去重

官网公告与 B 站官号动态使用同一套规则。分类为纯本地判断，不调用大模型；不确定的内容保留发送，不根据模糊标题相似度删除。

## 分类

主类别包括游戏活动、卡池与武器申领、版本更新与维护、研发情报、社区活动与福利、账号治理、版本前瞻与直播、干员介绍与演示、音乐与 MV、品牌联名与线下活动、节庆祝福、开奖结算和其他资讯。

分类优先读取标题与正文开头。研发通讯、版本公告、前瞻、联名、音乐等明确主题先于普通“活动”字样。正文中的签到、试用、维护、多活动与抽奖信息另存为标签，避免一篇卡池说明因附带签到被错分为签到公告。B 站分类前移除末尾的版本宣传段落，抽奖检查仍覆盖完整正文和转发原文。

B 站继续过滤所有含抽奖的动态，包括附带抽奖的干员演示、音乐 MV 和联名宣传；直播预约组件自带的奖励提示不单独触发过滤。官网记录抽奖标签，保留原有订阅范围。普通游戏内卡池与固定任务奖励不等同于社交抽奖。

## 活动识别与时间

活动优先采用明确的引号内名称，并结合活动类型、版本、开始与结束时间核对。仅提到“活动开启”等泛称时，不建立跨来源活动关联。版本更新和研发通讯可能包含多个活动，按完整文档标题比较，不能因为其中一个活动已通知就丢弃整篇公告。

每个事件单独记录阶段：活动说明、到点开启、提前开始提醒、结束提醒、维护提醒、内容更新、玩法指南和活动回顾。预告与实际开启分别保留。改期、更正、追加奖励等内容作为更新处理；更新、指南和回顾只有正文相同才合并，避免丢失新信息。

同一活动、同一阶段的两个通知，源时间差小于 86400 秒时才允许去重；恰好 24 小时或更久均保留。源时间采用原始发布时间，不使用采集时间、编辑时间或机器人发出消息的时间。定时提醒采用所提醒的开始或结束时间。不同活动期次、不同版本、冲突的起止时间保留。

## 投递

两插件共用 `data/endfield/notification_receipts.db`，记录按平台、机器人账号、群或私聊目标隔离。默认保留第一条成功发送的通知，另一来源遇到相同事件时跳过；不依赖哪个接口先抓到数据。

发送前以 SQLite 事务占用事件，另一来源遇到进行中的发送会等待重试。图片发送获得成功回执后才标记已发送；发送失败释放占用，进程退出留下的占用在 5 分钟后失效。成功记录保留 90 天，重启后仍参与比较。两插件必须使用同一数据目录；分别部署在独立目录或机器上不会共享去重记录。

多活动合并图逐项核对，最终发送的图片只包含尚未通知的活动或阶段。B 站只拆分有明确分节标题和独立开始时间的多活动正文；无法可靠拆分的内容整体保留，避免丢失新增信息。部分活动被移除后，B 站图片会重新渲染，并移除可能包含已通知活动的原始合并配图。接收平台成功发送但回执丢失，或进程在发送与记录成功之间退出时，仍可能重发，因此不承诺严格的一次投递。

这套实现不进行图片 OCR，也不能保证识别所有未来文案。B 站历史采集受限，本次规则依据已核实样本建立，类别数量不代表两个月的全量分布。
