# Tibo 后台推送修复（2026-09-05）

基线 `142df2c`。用户报告启动时能发图、后续更新图片发送失败，重启后积压补发。
没有获得正式环境失败日志，也没有操作生产账号，因此不把具体桥接层异常、
QQ 风控或上传大小限制写成已确认根因。

代码确认的可靠性缺口：图片或渲染失败后没有降级，游标一直停留；默认一轮
最多推送 20 条 / 7 页；启动任务与定时任务缺少覆盖采集及发送全程的共同锁；
待发送数据重试依赖本轮采集成功；空发送回执也被当成成功。

另一个已复现的路径：原启动任务使用触发上线的账号，后续定时任务使用全局
“最近上线”账号；存在多个登录账号时，后续可能切换到不在订阅群的账号。
故障测试模拟“账号 A 启动成功 → 账号 B 成为全局账号 → 再次定时推送”，
修复后两轮都由 A 投递。此为代码层确认的问题，不据此断言用户现场必然是多账号。
隔离回放基线 `142df2c` 的结果为 A 发送 1 次、无关账号 B 发送 1 次；同样输入
在修复版为 A 发送 2 次、B 发送 0 次。仅模拟传输，不对真实群发送测试消息。

## 行为

- 当前桥接端支持 `upload.create` 时，上传 PNG 后发送返回的 URL。每次新上传，
  不复用跨周期/重连后可能失效的 URL，也不依赖两台机器共享临时文件。
- 不支持上传时兼容原来的内嵌图片；图片或渲染失败后发送中文文字摘要，保留
  原文、翻译、模型解读标签与每条原帖链接。长文字明确提示去原帖查看全文。
- 图片或文字必须收到带消息 ID 的回执才推进该页游标。空回执不进行文字绕过，
  因为它也可能表示发送拦截器主动取消；全部失败或取消不会跳过帖子。
- 采集先写本地资料库，发送进度单独记录。上游失败仍重试已保存的待发帖子，
  但不在失败周期初始化新订阅的历史基线。
- 同一进程启动任务和定时任务互斥，通知本身也防重入。订阅绑定账号身份，
  上线/重连时更新该身份对应的连接对象；不因其他账号上线而更换发送者。
  已绑定账号不在线就暂缓，不尝试用其他账号向该群发消息。
- 新订阅绑定执行命令的账号；旧订阅在第一次成功投递后补记绑定。若旧订阅
  无法成功投递，可让管理员对目标机器人再执行 `/tibo 订阅` 指定发送账号，
  保留已发送游标。明确更换发送账号时重置旧账号遗留的失败退避。
- 默认每群每轮最多 **1 页 / 3 条**。积压按原顺序逐轮补发，不批量清空历史。
  `TIBO_RADAR_SUBSCRIPTION_MAX_PAGES` 可设 1–10；仍受原有
  `TIBO_RADAR_SUBSCRIPTION_BATCH` 条数上限约束。
- 图片和文字均失败时持久化指数退避：60、120、240……秒，上限 1 小时，
  到期后在下一采集周期重试。重启不会清掉退避或已确认的进度。
- 订阅状态显示最后发送方式（图片/文字兜底）和失败次数。日志只记录阶段、
  异常类型、图片字节数及游标，不输出桥接异常中的整段 base64 或凭据。

数据库只新增 `delivery_failures`、`retry_after`、`last_delivery_error`、
`last_delivery_mode`、`account_key` 五列（以及兼容更早版本的 `baseline_pending`）；保留现有
帖子、群订阅和游标。回滚代码可以忽略新增列，不需删除数据库。

这是有界、带回执的至少一次投递，不声称端到端“恰好一次”：桥接已接收但响应
丢失，或发送成功后进程在提交游标前崩溃，仍可能重复。不会用提前写游标掩盖
失败而丢失通知。单个上传/渲染/发送步骤有 30 秒超时，取消会正常向上传播。
