# End 查询性能优化与实测

测试日期：2026-09-05。分支：`perf/endfield-query-latency`。

对照基线是结构重构后的 `877a3165021858f6d834ff5a5c984b4999d854d6`，
优化代码是 `aad06cfd9313c198083b24b6f9612dba80e649c1`。
四轮基准均从干净工作区运行。未修改 `main`，未将独立 UI 预览接入正式插件，
没有运行 QQ/Satori 收发、签到、账号同步或其他生产任务。

## 结论

本次收益主要在重复查询与相同请求并发：公开接口联网实测中，配装热查询
从 1.447 秒降到 0.077 秒，耗时减少 94.7%；四个相同配装请求全部完成
从 5.762 秒降到 0.950 秒，减少 83.5%。
装备名称候选查询首次从 0.741 秒降到 0.339 秒，减少 54.2%。

不能据此说“整个插件所有查询都快了 95%”：配装冷缓存仅减少 6.8%，
武器关联冷缓存由 114.8 ms 变为 121.4 ms，本轮没有收益。
联网与固定数据回放中，武器关联的首次建索引都有少量额外开销，
因此这项优化适合重复查询，而不是加速首次查询。

## 改动与行为边界

- 装备候选匹配只读取装备目录，不再为了匹配名称请求每个套组的效果详情。
  正式装备目录卡片仍默认加载完整详情、属性及套装效果。
- 复用名称的拼音、首字母和音节计算。两个 LRU 缓存各限制 4,096 项；
  超过 256 个字符的输入不驻留。匹配评分、候选排序、别名读取及交互顺序不变。
- 武器与干员关联按武器类型、候选目录内容建立索引，同类型的不同武器可复用。
  仍保持“默认武器使用者优先，否则使用推荐名单”的规则及名称顺序。
  索引最多 16 项、1 MiB 的序列化内容计量，TTL 60 秒；并发构建合并。
  详情请求失败时仍返回可用的部分结果，但不缓存不完整索引。
- 配装仍按原流程解析参数、获取数据、计算完整视图；仅将最终视图内容和
  渲染版本作为图片缓存键。属性、等级、潜能、装备锻造、图标、效果或
  数据版本变化都会使用不同缓存键。最多 32 项、24 MiB PNG 内容、TTL 60 秒。
  相同视图并发只渲染一次；缺少应有素材或渲染异常不会留下成品缓存。
- 开发者缓存清理已覆盖新增缓存，状态显示新增配装图片缓存统计。
  养成统计的账号详情、资源目录、名称映射改为同时启动，保留原来的名称源失败降级。

TTL 为固定过期时间，命中不续期。关联索引是一层新的短期缓存：底层公共 HTTP
缓存仍为原有的默认 600 秒，在过期边界附近，详情变更可额外延迟最多约 60 秒
反映到关联名单。配装图片会重新核对当前视图，但同 URL 素材内容变化仍可能
在图片 TTL 内复用旧图；可通过现有缓存清理命令立即失效。缓存上限描述的是
内容计量，不是整个 Python 进程的 RSS 上限。

没有降低画质、缩小图片、删减字段或调整网络重试/备用素材源策略。
没有增加浏览器渲染线程数，也没有给私人账号数据增加新的共享缓存。

## 测试口径

使用同一台 Linux 6.8 / x86_64 虚拟机，16 vCPU，CPU 型号为 AMD EPYC 7B13，
Python 3.12.3。沿用项目现有环境：Entari 0.17.4、Playwright 1.62.0 / Chromium 151、
Pillow 11.3.0。各版本按顺序运行，未同时运行 pytest 或其他基准任务。

调用的是实际插件代码和公开数据接口，不是用固定 sleep 模拟业务耗时：

| 用例 | 实际入口与输入 | 不包含的部分 |
| --- | --- | --- |
| 装备名称候选 | `_collect_candidates("equipment", "长息轻护甲", "fz")` | 最终装备卡片绘制、发送 |
| 武器关联 | `find_weapon_operator_names`，赤缨 / `wpn_claym_0017` | 完整武器卡片查询、绘制、发送 |
| 配装 | `_handle_loadout`，`莱万汀 熔铸火焰 长息轻护甲`，默认等级/潜能/锻造 | 仅替换最终图片发送；包含名称匹配、数据、计算、素材、浏览器出图 |

每个版本、每种模式、每个用例各测：冷缓存 3 次、热缓存 5 次、四并发 3 批。
表中为相应中位数，“耗时减少”按 `1 - 优化后 / 优化前` 计算。

- 冷缓存：清空 HTTP、业务索引、成品图、拼音缓存；浏览器已预启动，
  HTTP 连接可以复用。因此不是“进程从零启动”耗时。
- 热缓存：紧接冷缓存最后一次成功调用，不清缓存。
- 四并发：每批清空业务索引和成品图，保留 HTTP、拼音缓存；
  测量四个相同请求全部完成的时间，不是缓存图片直接返回四次，
  也不是四个不同请求或整台机器的吞吐上限。
- 所有模式均不计 QQ/Satori 传输、用户交互等待和进程/浏览器启动。
- `live` 包含真实公开接口网络等待；`replay` 读取录制的相同公开响应和素材，
  不模拟网络延迟，只用于固定输入下的处理/渲染比较和输出校验。

每份 JSON 都包含提交号、工作区状态、测试时间、每轮耗时、HTTP 请求数、
响应字节、失败列表和每次输出的签名。没有账号、Token 或 Cookie。

在已安装项目依赖和 Playwright Chromium 的 Python 环境中，从仓库根目录执行：

```bash
git fetch origin
git switch perf/endfield-query-latency
git worktree add --detach ../otae-endfield-before 877a3165021858f6d834ff5a5c984b4999d854d6

python scripts/benchmark_endfield_queries.py --repo ../otae-endfield-before --mode record --output output/endfield-performance/before-live.json
python scripts/benchmark_endfield_queries.py --mode live --output output/endfield-performance/after-live.json
python scripts/benchmark_endfield_queries.py --repo ../otae-endfield-before --mode replay --output output/endfield-performance/before-replay.json
python scripts/benchmark_endfield_queries.py --mode replay --output output/endfield-performance/after-replay.json

python -m pytest -q tests/test_endfield_query_optimization.py
python -m pytest -q --junitxml=output/endfield-performance/tests.xml
```

四个基准命令请顺序运行。默认每用例为 3 次冷缓存、5 次热缓存、3 批四并发；
可用 `--cold-runs`、`--warm-runs`、`--concurrent-runs` 增加样本，
或用 `--cases equipment_search,weapon_relations` 排除出图用例。

`record` 将当时的公开响应保存到默认 `output/endfield-performance/public-http`，
后续两个 `replay` 使用同一目录，也可通过 `--cassette` 指定。
仓库只提交指标报告，不提交上游文章、数据表和素材的整份录制内容；
重新录制时上游可能已更新，输出哈希不保证与本记录相同，
应比较复测当天优化前后两份结果。

脚本在临时工作目录运行真实查询，拒绝非白名单域名、非 GET 和带认证头的请求，
只替换最终发送，不启动 Bot。没有图片输出、缺失回放数据或查询异常时会返回非零退出码，
报告内的 `http_failures` 也应核对为空后再解读性能。

本次尚未验证不同配装的并发吞吐、QQ 端到端延迟、生产缓存命中率及长时间驻留内存。
这些需要生产环境的脱敏日志或单独压测，不能从本次同请求缓存测试外推。
