# Grok Bot 应用接入

`grok_bot` 插件连接 Cursor Grok Bot 云端电脑的 HTTP 网关。Windows 机器人
通过 Tailscale 私网或 SSH 隧道访问该网关。使用登录账号里的 Grok Bot，
无需配置 xAI 模型 API Key。网关为未公开的内部接口，应用升级后可能需要适配。

## 开启与使用

**默认关闭，包括升级后的已有群。只有 SuperUser 可以手动开启。**
先完成下方连接配置，重启机器人，再由 `.env` 的 `SUPERUSERS` 中的用户
在需要使用的群执行：

```text
/功能 开启 grok
/grok 你好，多惠
```

- `/功能 列表`：查看本群插件状态，Grok Bot 会注明仅 SuperUser 可开启。
- `/功能 关闭 grok`：SuperUser、本群管理员或群主可关闭；管理员和群主不能重新开启。
- `/grok 问题` 或 `/grokbot 问题`：文字或图片问答。开启后，本群成员均可使用。
- 引用消息后发送 `/grok 问题`：附上引用正文和图片；引用自带的 @ 由公共命令层处理。
- `/help grok`：未开启时也可查看接入说明；开启后可用 `/grok 帮助`。
- `/grok 修复会话`：仅 SuperUser 可执行，用于首次创建失败后遗留的待确认记录。
  创建超时或断连后，插件会自动核对并恢复，通常不需要执行；只有提示云端存在
  重复或同名 Bot 时，才需要先在应用中核对。修复须在出错的群或私聊执行，随后重新提问。
- 私聊也默认关闭。SuperUser 可以在自己的私聊执行 `/grok 开启`、`/grok 关闭`。
  普通用户不能自行开启；授权一个群不会开启成员的私聊。

开关仅影响接收命令的机器人在当前会话的使用，保存到
`data/group_manager/switches.json`，重启后保留。开关命令不会创建云端 Bot，
首次实际提问时才创建。关闭后，已排队但未处理的问题不再发送；
已提交的云端任务可能继续运行并完成回复。

## 图片与文件

- 在同一条消息中发送 `/grok 看看这张图` 和图片，或引用一条有图片的消息后发送该命令。
- `/grok` 只附图片、只引用图片也可以，会默认要求描述并分析图片。
- 当前消息的图片排在引用图片之前，合计最多 3 张，每张原始大小最多 5 MB。
  支持 PNG、JPEG、WebP、GIF 等 Pillow 可解码格式；输入转为最长边 2048 像素的 JPEG，
  自动旋转、透明背景铺白，动图取第一帧；超过 2000 万像素会要求先压缩。
- 图片内容先上传到 Grok Bot 网关，再随本次问题提交给该会话绑定的 Bot。
  下载或上传失败会明确报错，不会忽略失败的图片继续提问。
- Grok Bot 在本次回复中发送的图片和文件，会下载原始内容后转发到当前群或私聊。
  仅有附件、没有文字的回复也会发送。单个最多 20 MB，每次最多 10 个、合计 50 MB；
  超限、下载失败或适配器发送失败时会提示对应附件，保留正文和其他成功的附件。
- 已完成的正文会先转发。附件由独立任务逐个下载、逐个发送，大文件下载不会阻塞后续正文。
  同一轮连续接收的回复共用上述大小、数量限制，追加输入不会重置额度，重复轮询不会重复发送正文或附件。
- 回复附件累计最多等待 60 秒下载，不计等待模型输出和 QQ 上传的时间；读取云端文件时
  先检查大小，再分块下载。下载和转发期间仍可追加输入；应使用独立文件名交付各次成品，
  避免覆盖尚未取回的文件。不同 Bot 仍共享云端文件系统。
- 图片使用 Satori 图片消息。LLOneBot 文件通过同一适配器的
  `internal/onebot11/upload_group_file` 或 `upload_private_file` 上传并发送，
  无需另外配置 OneBot 地址或密钥；其他适配器使用 Satori 文件消息，需要支持文件发送。
  SVG、TIFF 等无法直接显示的图片格式按文件发送，保留原始内容。

这里转发的是应用回复中实际附带的图片和文件。只在正文写出一个云端路径，
不会自动把该路径读成附件；默认人设已要求使用应用附件功能交付成品。
本轮初始输入之前的文件、用户输入附件和内部工具记录不会转发。
云端路径只通过网关读取，不会被当作 Windows 本地路径打开；
公开 HTTP/HTTPS 附件另行下载，不向这些地址发送网关 Token。

## Windows 配置

在机器人项目根目录的 `.env` 中填写：

```dotenv
GROKBOT_GATEWAY_URL=http://100.x.x.x:1340
GROKBOT_GATEWAY_TOKEN=填写网关Token原文
GROKBOT_TIMEOUT=300
GROKBOT_MAX_PENDING=8
GROKBOT_MAX_CONCURRENT=4
GROKBOT_PERSONA_FILE=
# 可选：原 QQBOT UUID，仅供只读诊断，问答不再发送到这个 Bot
GROKBOT_AGENT_ID=
```

网关 Token 来自 Grok Bot 云端电脑的 `/home/box/agent-data/gateway.json`
或 `/home/box/sand-data/gateway.json`。通过自己的安全文件传输方式保存到本地
配置，不要把 Token 发到 QQ、日志或 Git。它与 Cursor API Key、Tailscale 登录凭据不同。
基址只包含协议、主机和端口；`0.0.0.0` 是监听地址，应替换为云端电脑的
Tailscale IP 或 MagicDNS 名称。无需添加 `/v1` 或 `/api`。

网关请求固定直连，忽略 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 和 HYW 代理。
请求不会跟随重定向，也不会把网关错误正文发到 QQ。

两端加入同一个 Tailscale 私网后，在 Windows PowerShell 检查连通性：

```powershell
curl.exe --noproxy "*" --connect-timeout 10 "http://100.x.x.x:1340/health"
```

该检查无需 Token。填写 `.env` 后，在项目根目录运行只读检查：

```powershell
.\.venv\Scripts\python.exe -m plugins.grok_bot.check
```

检查验证网关健康、认证、Bot 列表与本地人设模板；若填写 `GROKBOT_AGENT_ID`，
也检查这个参考 Bot 的任务状态。不会创建 Bot、发送模型任务或输出密钥。
检查通过后，由 SuperUser 开启目标群，再进行实际问答测试。

## 会话与并发

每个会话对应一个新建的云端 Bot：

| QQ 场景 | 会话范围 |
| --- | --- |
| 同一个群的不同成员 | 共用本群对话，发言者 ID 随问题发送 |
| 不同群 | 各自独立 |
| 同一用户在群内与私聊 | 各自独立 |
| 不同用户的私聊 | 各自独立，分别授权 |
| 不同机器人账号或平台 | 各自独立 |
| 有多个频道的平台 | 群下不同频道分别独立，开关仍按群控制 |

新 Bot 名称类似 `多惠·群100·1234abcd`，使用本地人设创建。
**原 QQBOT 和它的历史记录会保留，但不再用于新问答。** 不复制旧 Bot 的
历史、记忆或自动化，也不会在独立 Bot 出错时退回共享 Bot。

会话映射和安装标识保存到 `data/grok_bot/sessions.json`；云端保存对应 Bot 的
对话历史。请同时保留本地数据和云端 Bot。迁移 Windows 部署时需复制完整的
`data/grok_bot` 与 `data/group_manager`，不要把同一套数据同时运行在多个机器人进程。
不要删除映射文件来清理队列，否则会丢失原会话的对应关系。

**同会话可以在云端任务尚未结束时追加输入，每个会话只有一个回复接收任务。**
图片准备、上传和输入提交按接收顺序执行，不等待前一项云端任务完成；具体何时执行、
是否合并回答由 Grok Bot 决定。同群其他成员的补充也可能改变当前任务方向。
不同会话默认最多 4 个同时接收回复，同群追加输入不额外占用会话名额。
`GROKBOT_MAX_PENDING` 限制等待提交或正在准备、上传、提交的输入，默认 8，范围 1～32；
收到网关提交响应后释放输入名额。`GROKBOT_MAX_CONCURRENT` 限制接收任务数，范围 1～16。

引用规则按本轮连续对话判断：

- 本轮只有初始输入：正文和图片引用最初的 QQ 问题；文件先发引用该问题的文件提示，再单独上传。
- 又提交了新的 `/grok` 或 `/grokbot` 输入：后续回复直接发送到当前群或私聊，不强行归给某一条问题。
  同一个人追加也算；普通群聊消息不算。图片准备失败或网关明确拒绝提交的输入不算成功打断。
- 引用规则在实际 QQ 发送前检查，下载或上传期间追加输入，也会影响尚未发出的图片。
- 云端会话有额外输入，或接入时已有未结束的云端工作：取消引用，继续接收本轮锚点之后的输出。
- 云端工作结束、回复连续两次检查稳定、附件发送完成后，本轮接收结束；下一条问题重新作为初始输入。

每条输入从进入队列到提交，最多等待 `GROKBOT_TIMEOUT` 秒；每轮接收获得会话名额后，
创建 Bot、同步人设、提交和接收输出合计也受该时限约束。追加输入不重置本轮接收时限。
默认 300 秒，范围 30～1800；长任务可设为 900。超时只停止本地接收，不终止云端任务。

每个独立会话会占用一个云端 Bot 名额，仍受账号的 Bot 数量限制和订阅额度限制。
对话隔离不等于电脑隔离：同一账号的 Bots 仍共享云端电脑的文件系统、浏览器和工具连接。
人设要求不访问其他会话的记录，但它不构成文件系统权限隔离。
见 [Cursor Grok Bot 工作方式](https://cursor.com/docs/grok-bot/work)。

## 花园多惠人设

默认模板：[plugins/grok_bot/persona.md](../plugins/grok_bot/persona.md)。
以花园多惠的音乐热情、天然随性的思考方式和对兔子的喜爱为基底，使用中文。
闲聊简短温和，偶尔自然跳脱；技术问题先讲清事实与步骤，不为角色效果编造答案。
没有固定猫娘口癖，不把每个话题都转到吉他，也不硬编码搜索服务故障。
模板中的对话示例为原创。

音乐和性格参考官方的[角色介绍](https://bang-dream.bushimo.jp/collabo/railgun_t/)，
QQ 回答习惯和会话约束是本项目的角色设计。

可以直接编辑默认模板，也可以用 `GROKBOT_PERSONA_FILE` 指向自定义 UTF-8 文本，
支持 Windows UTF-8 BOM；相对路径以机器人项目根目录为基准，内容须为 1～20000 字。
编辑模板内容后，**每个会话在下一轮接收启动时同步人设**，保留对话和 Bot 的名称、头像设置。
修改环境变量中的文件路径或并发配置后建议重启机器人。
不要在云端单独修改受管 Bot 的描述作为长期配置，它会被本地模板同步覆盖。

## 异常与恢复

插件用本轮初始输入的唯一请求编号定位输出，检查各条输入的接收记录、Bot 状态、后台任务和子任务，
只读取该锚点之后的完整回复，忽略旧答案、工具记录和流式预览。
每轮默认间隔 1 秒：应用已经发送完成的消息会在读取到后转发，不等后台任务全部结束，
也不等所有附件下载完成；实际到达时间还受网关与 QQ 接口耗时影响。
本轮后续发送的新正文和附件会继续追加，前一项任务晚到的附件也会接收，已转发的部分不会在结束时重发。
若云端改写了已经转发的正文，插件会停止继续拼接并提示在应用中查看。

只有旧格式的普通 assistant 记录、没有明确发出消息时，仅在未被打断的本轮对话中，
等两次空闲确认后使用最终正文。多条输入交错时只转发明确发出的消息，避免把内部记录当作回复。
需要人工确认时，仍需在应用中处理。会话正在接收回复时不能执行绑定修复；
修复进行中到来的输入会先等修复结束，不会同时修改绑定。

超时或网络中断不代表云端任务停止。插件不会盲目重发问题或终止现有任务；
下次输入可以提交到仍忙碌的云端会话，但新接收任务只转发新锚点之后的输出，不补发停机期间的历史。
重启机器人清除本地等待队列，云端工作可能继续；退出时会取消并回收接收和附件工作任务。

状态、接收记录、会话记录与附件分块等只读接口遇到临时网络异常，或 HTTP
408、429、500、502、503、504 时，最多尝试 6 次，按 1、2、4、8、16 秒指数退避，
重试等待合计 31 秒，可跨过 20～30 秒的 Tailscale 中继断连。重试受现有任务或附件下载
总时限约束，不重新计时：`GROKBOT_TIMEOUT` 到期即停止等待。创建 Bot、发送问题、上传图片、
修改 Bot 和中断任务等写入操作不会在网关层自动重试，避免响应丢失后重复执行；
创建 Bot 和发送问题先按下文的方式核对结果，再决定是否补发一次。
认证失败、接口不存在、参数错误和不兼容的返回内容也不会重试。

发送问题时连接被拒、连接被对端关闭（`RemoteProtocolError`、`ReadError`、`WriteError`）
或读取超时，插件会用同一个 `clientNonce` 查询 `promptAcceptanceStatus`：

- 云端已记录（`pending`、`accepted` 或 `rejected`）：视为已提交，不重发，由接收任务继续跟踪；
- 明确 `not-found`，且连接已被拒绝或关闭：用同一个 `clientNonce` 和相同内容补发一次，
  补发再失败只报告错误，不发第三次；
- 读取或写入超时后即使 `not-found` 也不重发：TCP 可能在链路恢复后才把原请求送达；
- 查询本身失败（已按上面的退避重试）或返回 `unknown-durability`：报告原错误，不重发。

`getAgentTranscriptTail` 和 `createAgent` 的单次读取超时为 60 秒，其他普通网关请求为 20 秒，
连接超时均为 10 秒。这与整项任务的 `GROKBOT_TIMEOUT` 分开：超过任务时限会提示
“本轮接收等待超过……秒”；`ReadTimeout` 表示单次读取等待超时；`ReadError`、
`RemoteProtocolError` 等表示读取或 HTTP 协议异常，不能仅凭长任务就认定是总时限导致。
日志会记录接口名、异常类型或状态码、尝试次数、单次耗时、是否重试，以及原始异常的
类型、消息和调用链（最后一次失败时附 traceback，只有文件、行号和源码行，不含变量值）。
不记录 Token（若出现在异常消息中会替换为 `<redacted>`）、提问内容或响应正文。
面向 QQ 的提示文字不变。原始异常保留在 `GatewayError.__cause__`，但去掉了它的栈帧：
entari 的 loguru 开启 `diagnose=True`，会渲染栈帧变量，发请求那一行的变量含认证头。

创建 Bot 前会保存待确认记录，带写入时间 `pending_since`。连接尚未建立，或创建被网关以
HTTP 400、401、403、404、422、429 明确拒绝时，会清除本次失败的记录，下次提问可重新尝试。
HTTP 400 表示网关拒绝请求，具体原因仍需结合云端日志判断；可能涉及参数校验或
Bot 数量限制，不能仅凭状态码认定为 Token 错误。

创建请求只发送 `name`、`description` 和 `isIntroductionSuppressed`，会话标记
写入人设描述的独立一行，不要求网关保留可选的 `purpose` 字段。旧版 `purpose`
标记仍可识别，并会在下次提问同步到描述中。本地 `nonce` 用于区分创建尝试，
不发给网关，也不假设创建接口支持幂等重试。

创建超时或断连后，插件立即用 `listAgents` 对账（按上面的退避重试），只按会话标记匹配：

- 恰好一个 Bot 带本会话标记：已在云端创建，直接绑定并继续本次提问；
- 没有：可能是请求未到达，也可能云端还在处理。等到这次创建开始满 90 秒
  （60 秒读取超时、10 秒连接超时再留余量）后重新列出，仍没有才清除待确认记录，
  并在同一次请求里重试创建一次。连接被拒绝时请求肯定没有发出，链路恢复后立即重试；
- 重试仍然超时：保留待确认记录并提示“创建结果暂未确认”，不会第三次创建；
- 有歧义时不绑定：出现多个带本会话标记的 Bot，或存在同名但没有会话标记的 Bot，
  都保留待确认记录并停止发送，请管理员在应用中删除重复项、核对或重命名同名 Bot。

待确认记录不会锁死会话：之后每次提问都会重新对账，歧义消除即自动绑定；没有对应 Bot
且记录已超过 90 秒，就清除并重新创建。旧版没有 `pending_since` 的记录视为已过期，
下次提问直接对账。HTTP 5xx 或无法识别的返回值同样保留记录，由下次提问对账。
映射冲突、已绑定的 Bot 丢失或文件损坏时仍会停止发送。

`/grok 修复会话` 仍可由 SuperUser 手动执行：

```text
/grok 修复会话
/grok 你好，多惠
```

修复命令先查询云端：能找到会话标记就恢复绑定；没有对应 Bot 才清除当前会话的
待确认项，最近 90 秒内发起的创建会提示稍后再修复。它与当前会话的接收任务互斥，
不创建或删除云端 Bot，不清空已绑定会话的历史，也不修改其他群的记录。
存在同名但没有会话标记的 Bot 时，会要求管理员核对身份。
不要删除整个 `sessions.json`，也不要随意填入其他会话的 ID。

运行中的插件每次读取绑定时都会检查 `sessions.json` 是否被替换，离线工具或手工清理
后无需重启即可生效；运行中误删整个文件时继续使用内存中的安装标识，不会为所有会话新建 Bot。
文件内容损坏时停止使用并报错，不会用内存数据覆盖。

若云端 Bot 被手动删除，确认接受丢失该会话历史后，删除其对应绑定项，
下次提问会创建新的独立 Bot。在项目根目录执行离线工具，
它只删除选中的那一项，写入前自动备份，未确认云端状态时不要直接删除整个文件。
仍建议先停止机器人，避免与正在写入的绑定同时修改：

```powershell
python -X utf8 scripts/repair_grok_binding.py                       # 只读列出全部绑定
python -X utf8 scripts/repair_grok_binding.py --peer 123456         # 预演，不写盘
python -X utf8 scripts/repair_grok_binding.py --peer 123456 --yes   # 执行
```

`--peer` 是群号或私聊用户号，多账号平台再用 `--kind`、`--platform`、`--self-id`
限定；也可以直接用 `--agent-id` 指定失效的 Bot UUID。匹配到多项、文件结构不符或
写入失败时都会拒绝并保持原文件不变，`--yes` 执行前请先停止机器人进程。
脚本说明里“运行中的进程会把绑定项写回”指旧版插件；当前插件会重新读取被替换的文件，
停机只是为了避免两边同时写入。

## 云端连接恢复

云端使用 userspace networking 时，可在已登录的 Tailscale 上配置：

```bash
tailscale serve --bg --tcp=1340 tcp://127.0.0.1:1340
```

该配置只向私网转发，不启用公网 Funnel。`--bg` 保留 Serve 配置，但依赖
`tailscaled` 守护进程运行；仅通过 `nohup` 启动的进程不会自动跨机器重启恢复。
云端重启后运行自己配置的启动脚本，再检查 Windows 到 `/health` 的连接。

## 协议来源与验证范围

接口及字段参考 [grokbot-sdk c14347f](https://github.com/Adam91holt/grokbot-sdk/tree/c14347fa82d167b9a5984ec1baff56b2f074485a)
的网关类型定义和测试，Python 客户端直接使用现有 HTTPX，无需安装 Node.js。
涉及 `listAgents`、`createAgent`、`updateAgent`、`getAsyncTasks`、`getSubagents`、
`sendPrompt`、`promptAcceptanceStatus`、`getAgentTranscriptTail`，均使用 POST；
`/health` 使用 GET。

附件字段进一步核对了官方 Grok Bot 桌面客户端 0.30.0 的调用代码：
`uploadAttachment` 使用 `filename`、`bytesBase64` 与可选 `agentId`，返回 `path`；
`readAttachmentChunk` 使用 `path`、`offset`、`length` 与可选 `agentId`，返回
`bytesBase64`、`totalSize`、`mime`。插件使用分块读取原始图片和文件，
不依赖 `readAttachmentImage` 的图片预览大小限制。
版本、来源、校验值和脱敏结构样例见 [附件协议核对记录](grok_bot_attachment_protocol.md)。

自动测试覆盖会话映射、重启恢复、人设同步、并发和排队、创建拒绝与响应丢失、
SuperUser 会话修复、旧回复过滤、认证错误、图片上传、附件分块下载与转发、
后台忙碌时提前回复、下载期间追加正文、逐个附件交付、去重、取消与大小限制、部分失败，
同会话任务中追加输入、无追加时引用初始问题、追加后取消引用、上传期间引用切换、下一轮恢复引用，
只读接口断连恢复、分页重试、附件传输中断重试、写入不重试和总时限约束，
指数退避跨过约 25 秒断连、创建 Bot 的 60 秒读取超时与超时后对账（已创建即绑定、
