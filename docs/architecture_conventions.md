# otae-bot 架构规范

本文是新架构下写代码、改代码、上线时必须遵守的约定。每条规则后面的「原因」说明它防的是什么问题；标了「守卫」的规则由测试自动检查。

目录名以文件树整理之后的布局为准。

## 1. 总原则

1. **内部只有 Satori。** 不管外面接的是什么协议，进到 bot 里的只有 Satori 的事件、消息元素和接口。
2. **平台差异只在边界层消化。** Satori 表达不了的能力，要么在边界层补成标准或扩展元素，要么放弃，不往里漏。
3. **只用框架的公开接口。** 不改写、不替换 Entari 和 Letoderea 的内部实现。
4. **按能力判断，不按平台名判断。** 能发就发，发不了就降级，不写「如果是某某平台」。
5. **用户可见的行为变化必须是有意的。** 重构不改行为；要改行为就单独说明。

## 2. 分层与依赖方向

依赖只能从上往下，不能反向，也不能跨层。

| 层 | 目录 | 可以依赖 | 不可以 |
|---|---|---|---|
| 插件 | `plugins/<名字>/` | Entari 公开接口、`otae_bot` 下除 `boundary` 之外的包 | 其他插件；`otae_bot.boundary`；任何平台协议〔守卫〕 |
| 核心业务 | `otae_bot/groups`、`hypergryph`、`command_usage`、`delivery`、`pipeline`、`accounts`、`messaging`、`scheduling` | Entari 公开接口、`infrastructure`、`config` | `plugins`；`boundary`〔守卫〕 |
| 基础设施 | `otae_bot/infrastructure`、`config` | 标准库和第三方库；`config` 另可用 `arclet.entari.config`（Entari 的配置接口） | 其余 Entari；`plugins`；其他核心包〔守卫〕 |
| 边界层 | `otae_bot/boundary` | satori-python 的适配器和服务端 | `plugins`；核心业务包 |

- 插件之间不互相 import。需要共享的东西下沉到 `otae_bot`。〔守卫〕
- 装配应用的 `otae_bot/application.py` 是唯一可以 import `otae_bot.boundary` 的非边界模块。
- `otae_bot/compat`（NoneBot 风格兼容层）只减不增：新代码不得使用，改到哪个插件就顺手把那个插件迁到 Entari 原生写法。

## 3. 边界层

1. **唯一允许出现平台协议的地方**是 `otae_bot/boundary/`。OneBot 动作名、`internal/` 调用、平台的 HTTP 地址和令牌，都只能出现在这里。〔守卫〕
2. **继承上游适配器，只替换实测有问题的部分。** 不复制整份上游代码；不得已复制单个函数时，用一行注释说明。
3. **每个补丁必须有**：一句注释说明上游哪里不对，一个不联网的单元测试，以及一次对真实实例的实测记录（写在提交说明里）。
4. **解码永不抛异常。** 引用取不到、转发展不开、卡片解析失败，都降级成更简单的元素并记一条警告，不能让整条消息丢失。
5. **发出去的元素要能被 Satori 自己的解析器读回来。** 新增或修改元素输出时，测试里必须走一遍「输出 → 解析」。
6. **上游修好了就删补丁。** 升级依赖时逐个核对补丁是否还需要。

边界层对内的承诺（改动这些等于改接口，要同步改使用方和测试）：

- 成员角色 id 固定为 `owner`、`admin`、`member`，事件里和查询里一致。
- 引用带作者和内容；取不到时是不带子元素的 `<quote id>`。
- 合并转发是 `<message forward="true" id>`；只在被引用时展开子消息，深度和总数有上限。
- 平台卡片是带命名空间的扩展元素（如 `onebot:json`）。
- `features` 如实列出可用接口。

## 4. Satori 使用约定

1. **ID 是不透明字符串。** 不做 `int()`，不假设是数字，不从 ID 里解析含义。〔守卫〕
2. **guild 和 channel 是两个概念。** 不假设它们相等；需要群就取 guild，需要发送目标就取 channel。
3. **不按平台名或适配器名分支。**〔守卫〕需要知道能不能做某件事时，查账号的 `features`，或者直接尝试并处理失败。
4. **扩展元素可以读写，但必须容忍它不存在。** 读不到扩展元素时功能照常工作，只是信息少一些。
5. **发送要有降级顺序**，并且每一级失败只记一条日志。例如：合并转发 → 逐张图片 → 文字说明。
6. **监听事件用事件类**，不用类名字符串比较。〔守卫〕
7. **不长期保存消息 ID。** 不同接入方式的消息 ID 格式不同；需要跨重启引用消息的功能要单独设计。

## 5. 框架使用约定

1. **只 import 公开名字。** 不 import 下划线开头的名字和模块，不访问对象的下划线属性。〔守卫〕
2. **确实没有公开接口时**，把那一处私有用法收进 `otae_bot/pipeline/framework_hooks.py`，注释里写明缺的是哪个上游接口。其他地方一律通过它间接使用。当前只有一处：Letoderea 的全局传播器。
3. **不替换框架的函数和属性**（不做 monkeypatch）。要拦截出站调用，用 `APIRequest` 等公开事件。
4. **停止信号要放行。** 凡是写 `except Exception` 的地方，前面必须先有 `except ExitState: raise`，否则 `finish()` 会被当成错误吞掉。`asyncio.CancelledError` 同理。
5. **全局机制只装一次。** 群功能开关、指令统计这类对所有插件生效的东西，在应用启动时统一挂载，不依赖插件加载事件重复安装。

## 6. 插件

1. **固定三层：**
   - `handlers.py`：只做解析参数、调用 service、回复。要薄。
   - `service.py`：业务逻辑。新代码必须不 import Entari、不接触消息元素，可以脱离 bot 单独测试；已有代码改到时再迁。现状：21 个插件中只有 4 个（bilibilibot、endfield、radar、tibo_radar）拆出了 `service.py`（共 15 个文件），其中 `bilibilibot/service.py` 仍经 `otae_bot.compat` 用到 Entari，其余插件的业务逻辑多半还在 `handlers.py` 里。
   - `store.py` / `draw.py`：存储和渲染。
2. **回复用会话，推送用投递服务。** 指令处理函数里用 `session.send`；定时任务和后台任务里的主动消息一律走 `otae_bot.delivery.deliver`，不自己选账号、不直接调协议发送接口。
3. **群功能开关和指令统计是自动的。** 插件不需要、也不应该自己判断「本群是否开启」。
4. **数据放在 `data/<插件名>/`**，通过 `infrastructure/storage` 读写。不在插件目录里写运行时数据。
5. **插件目录名就是它的键。** 群功能开关和指令统计都按它存，用户输入 `/功能 关闭 xxx` 也用它。不要重命名已有插件。
6. **外部请求走共享的 HTTP 客户端**，渲染走共享的浏览器和线程池，不自建。
7. **缺配置时要能加载。** 没有密钥的插件应当正常加载，在被调用时给出「未配置」的提示。

## 7. 配置

1. **设置在 `entari.yml`，密钥在 `.env`。** `entari.yml` 不进 Git（从 `entari.example.yml` 复制）；`.env` 只放令牌、API Key、Cookie、加密密钥，由 `entari.yml` 用 `"${{ env.名字 :- }}"` 引用。第三方代码自己从进程环境读的变量（代理、证书、hyw-frontier）是唯一例外，列在 `otae_bot/config/settings.py` 的 `PROCESS_ENV`。
2. **段落固定。** `basic:` 归 Entari（连接、前缀、管理员、日志）；`otae:` 是核心设置（`otae_bot/config/core.py`）；`plugins: plugins.<目录名>:` 是插件设置；`plugins: server:` 声明 OneBot 接入。
3. **每个配置段是一个类型化模型。** 继承 `otae_bot.config.model.Settings`，每项写默认值和一句中文说明，用 `plugin_settings(<目录名>, 模型)` / `core_settings()` 读取。新增或改动配置项要同步 `entari.example.yml`（测试核对）。
4. **不直接读环境变量。** `otae_bot/config/` 之外不得用 `os.getenv` / `os.environ`。〔守卫 R8〕
5. **没配置也能导入、能加载。** 模块导入时可以读配置，但不得因为缺配置而失败；缺密钥时插件照常加载，用到时提示「未配置」。
6. **程序不写配置文件。** Entari 退出时会改写它加载的文件，所以加载的是 `.runtime/` 下的副本；不要让代码改写 `entari.yml` 或 `.env`。运行时会变的数据放 `data/<插件名>/`，不放配置里。

## 8. 数据

1. **键里带平台和账号的地方，序列化方式只有一份实现**，读和写都用它。迁移工具必须产出逐字节相同的键。
2. **改存储格式或键必须附带迁移工具**，并满足：
   - 默认只预演，只打印条数；加 `--apply` 才真改。
   - bot 运行时拒绝执行。
   - 修改前自动备份。
   - 可重复执行，第二次不产生变化。
   - 可以反向运行用于回滚。
   - 用线上数据的副本演练过正向和反向，条数写进提交说明。
3. **一次上线只做一种数据迁移。** 不把两种迁移叠在一起。
4. **凭据类数据不外传、不复制到开发机。** 需要了解其结构时，只远程查询条数和键的形状。

## 9. 测试

1. **在协议层面测，不伪造框架内部对象。** 新写的测试必须用真实的 Satori 事件和假的协议调用驱动，不要用 `SimpleNamespace` 冒充事件和会话；已有测试改到时再迁。伪造内部对象的测试会在升级框架时成片失效。现状：112 个测试文件中 57 个用到 `SimpleNamespace`（共 409 处），其中至少 40 处（18 个文件）直接拿它冒充事件或会话。
2. **守卫基线只能缩小。** `tests/fixtures/boundary_guard_baseline.json` 里的条目只许减少；新增违规会让测试失败，不允许靠更新基线来放行新违规。
3. **每次提交前跑全量测试。** 提交说明里写通过数，以及仍然失败的是哪些已知用例。
4. **改动收发消息路径必须实测。** 用测试账号在测试群里跑一遍，并且开着双向限制：只接收测试群的消息，只允许向测试群发送。单元测试通过不等于链路通。
5. **实测发现的问题要补成单元测试**，再修。
6. **已知不稳定的用例要登记**，不能默默重跑到通过为止。目前有四处：`test_hyw_retry`（与执行顺序有关，单独运行通过）、`test_bilibili_poller` 里的一个用例，以及 `test_browser_render_queue` 和 `test_http_asset_broker` 里各一个计时用例（高负载时偶发）。

## 10. 提交与分支

1. **`main` 始终可部署。** 架构改动在独立分支上做，合并或推送到 `main` 之前先确认。
2. **一个提交只做一件事。** 移动文件和修改逻辑分开提交；移动的提交里不夹带行为变化。
3. **提交说明格式：** `类型(范围): 摘要`，正文说明改了什么、为什么、怎么验证的。中文。
4. **不带署名。** 不加 `Co-Authored-By` 或任何工具生成的标注。
5. **每个提交都要被更新日志收录。** 合并前在 `plugins/changelog/changelog.json` 补上对应的版本条目。
6. **说明里只写验证过的事。** 没实测的要写明「未实测」。

## 11. 依赖升级

1. **版本锁定。** Entari、satori-python、适配器都写死版本号，不用范围。
2. **升级步骤：**
   1. 在独立环境里装新版本，跑全量测试，对比升级前后的失败列表。
   2. 逐个核对 `boundary/` 里的补丁：上游修好的删掉，行为变了的重新实测。
   3. 核对 `framework_hooks.py` 里那一处私有用法是否还成立，上游有了公开接口就换掉。
   4. 用测试账号实测收发。
3. **不直接在线上环境里升级依赖。**

## 12. 上线与回滚

1. **上线步骤要事先写好**，包含每一步的回滚办法，并且回滚路径要演练过。
2. **涉及接入方式变化时先切一个账号**，观察一段时间再切其余的。
3. **切换前备份 `data/`。**
4. **线上环境的操作逐步确认**，不批量执行。
